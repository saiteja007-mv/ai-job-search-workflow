# Post-apply outreach (LinkedIn invites + recruiter emails for applied roles)

Run after applications are confirmed submitted. Working dir `/home/<YOU>/career-ops`.

## Standing rules
- Draft first, send only on explicit approval. LinkedIn invites and emails are separate approvals: "send the invites" means LinkedIn only; emails need their own "send emails".
- Frame the batch against the superagnt warm-outbound rules in `modes/_custom.md` (drafting-only methodology; superagnt MCP/credits blocked; no HeyReach/Instantly/AgentMail/Gmail lanes for superagnt). When the user asks "is this per superagnt", state honestly what matched and what didn't (discovery method, scoring, dedupe path, send path).
- US-based contacts only; skip anyone ever contacted (LinkedIn or email) and founders already reached via YC WaaS notes.
- Every proof point from `cv.md`/`cv-aiml.md`; voice-dna (no em dashes). For AI/agent roles include the <PROOF_POINT> in emails.

## Procedure
1. **Draft via GPT-6 Sol Codex** (`codex exec -m gpt-6-sol ... "$(cat prompt.md)"`, background + notify). Prompt: per company 2 contacts (tech recruiter + hiring manager), dedupe against contacts.json / outreach_log / reports / Unipile chats, find-only email discovery (SMTP confidence >=8 else EMAIL_UNVERIFIED), LinkedIn note <=300 chars (one verified contact fact + one CV proof + "I applied today for <role>"), email 90-140 words, Gmail DRAFTS only in jobmail, append to contacts.json with required schema (backup first), write `reports/outreach-applied-<date>.md` with counts. No sends.
2. **Review the report yourself** before posting. Flag and propose dropping: awkwardly worded notes, skip-level VPs, managers whose team evidence doesn't match the role (e.g. antifraud vs core ML). Recommend the trimmed set.
3. **Attach tailored resumes to Gmail drafts** (when asked): copy `output/<row>-*.pdf` to a scratch dir as `<YOUR_NAME>-Resume.pdf` (clean recipient-facing name), read each draft with `gog gmail drafts get <id> --account <YOUR_EMAIL> --json` (body is base64url in `draft.message.payload.body.data`; headers in `payload.headers`), then `gog gmail drafts update <id> --account ... --to <To> --subject <Subject> --body-file <f> --attach <pdf> --no-input`. `update` replaces the whole draft, so always re-pass To/Subject/body. Add one line "I've attached my resume for reference." before the sign-off. Re-`get` to verify `parts[].filename`.
4. **Send LinkedIn invites via the linkedin MCP only** (`tool_call`): `get_invite_budget` first (caps come from `lib/invite-ledger.mjs`, reconciled with LinkedIn's own sent count), resolve provider_ids via Unipile `GET $UNIPILE_API_BASE/users/<public_id>?account_id=<li account>` (also confirms current headline employer + US location), then `send_invitation` one at a time with `name`, `company`, `role`, `origin: "superagnt-warm-outbound"`. It dedupes and logs to the career-ops ledger itself; `scope: global` refusal = stop the batch. The MCP may flip the contact's `status` to `sent` itself, so when updating contacts.json afterwards match by name/LinkedIn URL, not `status == drafted`.
5. **Emails** only after separate approval. Re-grep each address across `data/outreach_log.json`, `reports/recruiter-outreach-*.md` and `~/.hermes/scripts` logs, then `gog gmail drafts send <id> --account <YOUR_EMAIL> --no-input` (~20 s apart). `drafts send` returns no message id, so verify with `gog gmail search "in:sent newer_than:1d" --account ... --plain` and confirm the drafts are gone from `drafts list`. Then record `emailSent`/`linkedinInviteSent` dates in contacts.json.
6. Report: who got invites, budget remaining, which drafts have which resume, and what still awaits approval.

## Invite budget and hygiene
- **Where the caps live:** `career-ops/lib/invite-ledger.mjs` (`SAFE_DAILY`, `SAFE_WEEKLY`; `OBSERVED_BLOCK` = weekly count at which the account was once restricted). The linkedin MCP, warm-outbound job and recruiter cron all read it. User-set caps: 35/day, 250/week. To change them: back up the file, edit the constants, then `systemctl --user restart linkedin-mcp.service` — the running MCP caches the old values until restarted — and re-run `get_invite_budget` to confirm.
- "How many are we actually sending": answer from `get_invite_budget` (`trailing7`, LinkedIn-side count) plus a per-day breakdown of `data/outreach_log.json` events whose `channel` contains `invite` (field `sent_at`). The dashboard's "BLOCKED" label only means trailing7 ≥ OBSERVED_BLOCK; it doesn't stop sends.
- **warm-outbound** (`~/automations/jobs/warm-outbound/`, systemd user timer ~09:40) reserves 10 of the shared daily pool for other lanes, so it sends 0 with `shared_pool_limit` once remainingToday ≤ 10. Its stderr goes to `logs/<date>.err`; check there first when it fails. Reproduce safely with `RUN_JOB_DRY_RUN=1 WARM_OUTBOUND_DRY_RUN=1 ~/automations/bin/run-job warm-outbound slack:<SLACK_CHANNEL_ID> -- ./run.sh`.
- **Withdraw stale pending invites** (lowers restriction risk at high volume): `python3 scripts/withdraw_old_invites.py 30 [--dry]` — pages Unipile `GET /users/invite/sent` (age from `parsed_datetime`; `date` is human text like "Sent 3 months ago"), `DELETE /users/invite/sent/<id>?account_id=...` paced 4–8 s, stops on 429/403, logs to `data/linkedin-invite-withdrawals-<date>.json`. Run in background with notify. Withdrawn people can't be re-invited for ~3 weeks.
